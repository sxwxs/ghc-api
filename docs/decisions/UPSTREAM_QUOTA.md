# 上游额度控制 — 设计文档

状态:待审阅,还没有实现。

## 1. 要解决什么问题

有些上游模型是按额度收费的,额度有有效期,比如每天发一笔,24 小时后作废。
所有请求都经过 ghc-api,所以由 ghc-api 在请求发出去之前判断:额度够不够。
不够就直接拒绝,不去调用上游。

## 2. 原则

- **通用。** ghc-api 不认识任何具体平台。怎么查额度、怎么认证,全在外置的"取数命令"里。
  代码、配置项、界面、报错、文档示例里都不出现平台名,只说"额度",单位是"点"。
- **默认不受限。** 没有配置的模型,行为和现在完全一样。
- **宁可少估,不要多估。** 拿不准的时候,按剩余更少来算。
- **账是近似值。** 不追求 100% 准确。两次取数之间的误差靠 `min_remaining` 兜底,
  每次取数后以上游数据为准。

## 3. 名词

- **一笔额度**:一个数量加一个过期时间。比如"250 点,明天 07:44 过期"。
- **取数命令**:一个外部程序,告诉 ghc-api"现在还有哪几笔额度,各剩多少,各什么时候过期"。
  和现在配置里"请求前拿密钥的命令"是同一类东西。
- **账**:ghc-api 在内存里记的当前剩余额度。每次请求扣一点,每次取数后以取回的数据为准重建。

## 4. 配置

在私有的 `upstream-proxies.yaml` 里。

```yaml
proxies:
  example-llm:
    quota:
      command: [/path/to/quota-command]
      refresh_interval_seconds: 3600
      command_timeout_seconds: 30
      min_remaining: 10
    models:
      limited-model:
        quota_cost: 2
      free-model: {}          # 没有 quota_cost,不受限
```

| 配置项 | 含义 | 默认值 |
|---|---|---|
| `quota.command` | 取数命令,字符串列表,不经过 shell | 必填 |
| `quota.refresh_interval_seconds` | 多久取一次数 | 3600 |
| `quota.command_timeout_seconds` | 取数命令最长运行多久 | 30 |
| `quota.min_remaining` | 安全阈值:请求之后剩余额度不能低于它 | 0 |
| `models.<id>.quota_cost` | 这个模型每次请求扣多少点 | 无,即不受限 |

- `min_remaining` 设成 0,表示额度可以全部用完。设成 10,表示剩 10 点的时候就不再放行。
- `quota_cost` 是大于 0 的数字,可以是小数(比如 0.5)。建议填偏大的数。
- 模型写了 `quota_cost`,但所在 profile 没有 `quota` 块,配置加载时报错。
- 取数失败后的重试间隔固定 60 秒,不做成配置项。

## 5. 取数命令的约定

标准输出是一段 JSON:

```json
{"batches": [
  {"amount": 250, "expires_at": 1794008691}
]}
```

- `amount`:这笔额度现在还剩多少,数字,不能为负。
- `expires_at`:过期时间,**整数的 unix 时间戳(秒)**。
- 两笔 `expires_at` 相同的,ghc-api 合并成一笔。
- `batches` 可以是空数组,表示现在没有额度。

下面任何一种情况都算**取数失败**:退出码不是 0、超时、输出不是上面的格式、
`expires_at` 不是整数、`amount` 不是数字或为负。

命令不能把密钥打印到标准输出或标准错误。ghc-api 只在界面上显示标准错误的前 200 个字符。

## 6. 每次请求怎么判断

只对配置了 `quota_cost` 的模型做,四种接口(responses、chat_completions、messages、systemone)都一样。
在模型和请求体校验通过之后、调用上游之前执行:

1. 把已经过期的额度去掉。过期时间提前 60 秒生效,避免时钟差几秒导致误放行。
2. 剩余总额减去 `quota_cost`,如果小于 `min_remaining`,返回 **429**,错误码 `quota_exceeded`,
   上游一次都不调用。
3. 否则先扣账,再发请求。扣的时候**先扣最早过期的那笔**,不够就继续扣下一笔。
4. 这一步在锁里完成,所以并发的请求不会一起通过检查。

"还没取到数"和"上次取数失败"都当作剩余额度为 0,所以受限模型一律返回 429。
错误信息会区分"额度不足"和"额度信息不可用",错误码相同。

### 退款

- 请求没能发给上游(连接失败、取不到密钥等):退款。
- 上游返回非 2xx:退款。
- 其他情况不退,包括读超时(请求已经发出,上游可能已计费)、流式响应中途断开、客户端取消。
- 退款退回到原来扣的那一笔,如果那笔已经过期,就不退。

这样会偏保守:上游其实没扣费的情况,我们这边也不退。上游在非 2xx 时仍然扣费的情况,
会在校准时被发现(见第 8 节)。

## 7. 什么时候取数

- **启动时**:`initialize_app` 里先同步取一次,最长等 `command_timeout_seconds`。
  失败不影响启动,只是受限模型暂时都会被拒绝。
- **之后**:后台线程按 `refresh_interval_seconds` 取数。失败后每 60 秒重试一次,直到成功。
- **配置热加载**:`upstream-proxies.yaml` 改了 `command` 或 `command_timeout_seconds`,
  这个 profile 的账清空,立即取一次数。profile 被删除,对应的账一起删。
  改 `min_remaining` 或 `quota_cost` 不需要重新取数。
- 同一个 profile 同时只会有一个取数在跑。取数命令运行期间不持有账的锁,请求不会被它拖慢。

取数完成后,新账 = 取回的数据(去掉已过期的)。还没结束的请求不会再扣一遍,
不管它是在取数开始前还是取数期间开始的:上游可能已经算进去了,也可能还没有。
所以账在两次取数之间是近似值,误差大约是"取数时还没结束的请求数 × `quota_cost`",
靠 `min_remaining` 兜底。

## 8. 校准和告警

目的:发现我们多扣了费、账和实际对不上的情况,提醒用户。

每次取数成功后,拿"取数开始那一刻我们账上的数"和"取回的数"按**每笔额度**(以 `expires_at` 为准)比较:

- 我们账上的**比取回的多**,说明实际扣得比我们记的多。产生一条告警。
- 我们账上的比取回的少,是 `quota_cost` 填得偏大造成的,属于预期,不告警。
- 取回的数据里有账上没有的新一笔(比如新发的额度),不告警。
- 账上有、取回的数据里没有的一笔,如果还没过期,按取回 0 比较(上游已经用完);已过期的不比较。
- 相差小于 0.01 点不告警。
- 上一次取数失败的,这次不比较,因为账是清零重建的。
- 第一次取数不比较。

告警内容:发生时间、profile、哪一笔(过期时间)、我们账上的数、取回的数、差多少。
**只放内存,每个 profile 最多留 50 条,重启后消失,不落盘。**
比较完之后,账以取回的数据为准。

## 9. 界面和接口

新增 `GET /api/quota`,返回每个配了 `quota` 的 profile:

- 当前剩余额度、`min_remaining`
- 每一笔额度的数量、过期时间、还剩多久
- 上次取数时间、上次成功时间、上次错误
- 告警列表

首页(`dashboard.html`)新增一块显示这些内容。没有任何 profile 配了 `quota` 时,这块不显示。

安全提示:这个接口只有数字,没有密钥和命令内容。它和 `/api/stats` 一样,不在
`PROTECTED_PATHS` 里,在开启认证时也不要求登录。

审阅结论:保持不受保护。首页的其他接口(包括请求正文)都不受保护,首页也没有传 token 的机制;
单独保护它只会让开启认证时这一块永远不显示。

## 11. 测试

用一个假的取数命令,不发任何真实网络请求。

- 先扣最早过期的;一笔不够会继续扣下一笔。
- 过期的额度不再可用;过期提前 60 秒生效。
- 剩余减去费用小于 `min_remaining` 时返回 429,且上游一次都没有被调用。
- `min_remaining` 为 0 时可以用到恰好为 0。
- 并发请求不会超扣。
- 没配 `quota_cost` 的模型完全不受影响。
- 退款:连接失败退、上游非 2xx 退、读超时不退、流式中途断开不退。
- 取数失败、没取到数、输出格式不对:受限模型一律 429。
- 取数失败后 60 秒重试;恢复后可用。
- 校准:账比实际多会告警;账比实际少不告警;新发额度不告警;只留最近 50 条。
- 配置:有 `quota_cost` 没有 `quota` 块报错;`quota_cost` 为 0 或负数报错。
- 热加载改了命令会清账并重新取数。

## 12. 不做的事

- **不落盘。** 账和告警都只在内存里,重启后重新取数。
- **只按次数计费,不按 token。** 每次请求固定扣 `quota_cost`。
- **默认单进程。** 多个进程各记各的账,互相看不见,只能靠校准事后发现。
- **不做重试和排队。** 额度不够就直接 429,由调用方决定。
- **不自动学习 `quota_cost`。**

## 13. 已知风险

- `quota_cost` 填小了,拦不住,只会在校准时告警。
- 取数命令挂了,所有受限模型都不可用。这是设计要求,不是缺陷。
- ghc-api 完全相信取数命令的输出,命令的可信度就是整套机制的可信度。
- 流式请求中途断开不退款,会少估剩余额度。
- 取数时还没结束的请求,取数完成后不会再扣一遍(见第 7 节)。如果上游在请求结束时才计费,
  新账会比实际多,直到下次取数;下次校准还可能把这个差额报成告警。靠 `min_remaining` 兜底。
- 退款和取数交错时(比如取数前扣账、取数后退款),账可能差一次 `quota_cost`,下次取数纠正。
- `max_connection_retries` 大于 0 时,读超时会重发请求,一次扣账可能对应上游多次计费。
  受限模型所在的 API 建议保持 0。
