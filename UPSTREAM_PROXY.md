# Configured Upstream Proxy

The configured upstream proxy is an isolated, optional subsystem for forwarding OpenAI-compatible Responses and Chat Completions requests, native Anthropic Messages requests, and System One decision requests, to private or self-hosted gateways.

It does not modify or share model routing with ghc-api's existing Copilot endpoints.

## Routes

For a profile named `example-llm`:

```text
POST /proxy/example-llm/v1/responses
POST /proxy/example-llm/v1/chat/completions
POST /proxy/example-llm/v1/messages
POST /proxy/example-llm/v1/systemone
GET  /proxy/example-llm/v1/models
GET  /proxy/example-llm/v1/models/<model_id>
GET  /proxy/models
```

`GET /proxy/models` is a first-party discovery catalog used by the built-in `/chat` page. It adds the profile name and profile base URL to each public model entry without exposing upstream URLs, headers, credentials, or affinity values.

Both model lists and the single-model route use the shared [model metadata
schema](docs/MODEL_METADATA.md), including context and output limits, input
types, and reasoning support. A detail response is the same object as its list
entry. Unknown models return HTTP 404 with `error.code: "model_not_found"`.

The existing `/v1/responses`, `/v1/chat/completions`, and `/v1/models` routes remain Copilot-only.

The legacy text Completions API (`/v1/completions`) is not part of this feature. `chat_completions` refers to `/v1/chat/completions`. `messages` is native Anthropic Messages passthrough; it is not translated to or from an OpenAI protocol. `systemone` is native decision-API passthrough and is likewise untranslated.

## Private configuration

The default private configuration path is:

- Windows: `%APPDATA%\ghc-api\upstream-proxies.yaml`
- Linux/macOS: `~/.ghc-api/upstream-proxies.yaml`

Override it with:

```text
GHC_API_PROXY_CONFIG=/path/to/private-proxies.yaml
```

Affinity state is stored separately in `proxy-affinity.json` under the ghc-api config directory. Override that path with `GHC_API_PROXY_AFFINITY_FILE`.

The proxy configuration is deliberately separate from `config.yaml`:

- It is not generated by `ghc-api --config`.
- It is not returned by `/api/runtime-config`.
- It is not merged into the existing Copilot model list.
- A missing or invalid file does not prevent the existing server from starting.
- On an invalid reload, the last valid in-memory configuration remains active.

Start from [`upstream-proxies.example.yaml`](upstream-proxies.example.yaml), but keep real endpoints, credential commands, headers, and model routes outside the repository.

## Profile configuration

```yaml
proxies:
  example-llm:
    enabled: true

    auth:
      type: bearer_env
      env: EXAMPLE_LLM_TOKEN

    headers:
      X-Quota-Id: ""

    affinity:
      enabled: true
      response_header: X-Route-Token
      request_header: X-Route-Token
      scope: model
      persist: true

    apis:
      responses:
        upstream_url: https://gateway.example.test/responses
        request_model: omit
        response_model: public

      chat_completions:
        upstream_url: https://gateway.example.test/chat/completions
        request_model: upstream
        response_model: public

      messages:
        upstream_url: https://api.anthropic.com/v1/messages
        request_model: upstream
        response_model: public
        headers:
          anthropic-version: "2023-06-01"
          x-api-key: "${ANTHROPIC_API_KEY}"

    models:
      example-coding-model:
        display_name: Example Coding Model
        reasoning: true
        input: [text]
        context_window: 128000
        max_output_tokens: 16384
        headers:
          X-Upstream-Model: example-route
        apis:
          responses:
            upstream_model: null
          chat_completions:
            upstream_model: example-chat-deployment
          messages:
            upstream_model: claude-sonnet-4-5
```

Profile names may contain only letters, digits, `.`, `_`, and `-`.

The example above does not enable the `systemone` API; decision models normally live in their own profile, shown under [Native System One decisions](#native-system-one-decisions).

A model that omits an entry from its `apis` mapping still enables that API with no `upstream_model`, so every API enabled on the profile must either be mapped by the model or disabled with `enabled: false` on it. Enabling an API with `request_model: upstream` while a model leaves its `upstream_model` unset is rejected at config load.

## Quota control

Some upstream models are billed against a quota that expires (for example one
batch per day, void 24 hours later). ghc-api can refuse a request before it
reaches the upstream when the remaining points are too low. This is generic:
ghc-api does not know any platform. How to query the quota and authenticate is
entirely inside an external command; configuration, UI, errors and examples
only talk about a "quota", measured in points.

Models are unrestricted by default. A profile opts in with a `quota` block, and
individual models opt in with `quota_cost`:

```yaml
proxies:
  example-llm:
    auth:
      type: none
    apis:
      responses:
        upstream_url: https://gateway.example.test/responses
    quota:
      command: [/path/to/quota-command]
      refresh_interval_seconds: 3600
      command_timeout_seconds: 30
      min_remaining: 10
    models:
      limited-model:
        quota_cost: 2
      free-model: {}          # no quota_cost, unrestricted
```

| Key | Meaning | Default |
|---|---|---|
| `quota.command` | command returning the current quota snapshot, as a list of strings, without a shell | required |
| `quota.refresh_interval_seconds` | how often to refresh | 3600 |
| `quota.command_timeout_seconds` | maximum runtime of the command | 30 |
| `quota.min_remaining` | safety threshold: remaining points must not drop below it after a request | 0 |
| `models.<id>.quota_cost` | points charged per request for this model | none (unrestricted) |

`min_remaining: 0` lets the quota be used up completely; `min_remaining: 10`
stops admitting requests when only 10 points are left. `quota_cost` is a
positive number and may be fractional (for example `0.5`); prefer rounding up.
A model with `quota_cost` inside a profile without a `quota` block is rejected
at config load. After a failed refresh, retries are fixed at 60 seconds and are
not configurable.

### The quota command

Standard output is a single JSON object:

```json
{"batches": [{"amount": 250, "expires_at": 1794008691}]}
```

- `amount`: points currently left in this batch, a non-negative number.
- `expires_at`: expiry as an **integer unix timestamp in seconds**.
- Two batches with the same `expires_at` are merged.
- `batches` may be empty, meaning no quota is available.

Any of the following counts as a failed refresh: non-zero exit code, timeout,
output not matching the format above, `expires_at` not an integer, or `amount`
not a number / negative. The command must not print credentials to stdout or
stderr; ghc-api only shows the first 200 characters of stderr on the dashboard.

### Request admission

Applies only to models with `quota_cost`, identically for `responses`,
`chat_completions`, `messages` and `systemone`, after model/body validation and
before the upstream call:

1. Expired batches are dropped; expiry takes effect 60 seconds early to avoid
   clock skew letting a nearly-expired batch through.
2. If `remaining - quota_cost < min_remaining`, ghc-api returns **429** with
   code `quota_exceeded` and never calls the upstream.
3. Otherwise the points are deducted first (earliest-expiring batch first,
   continuing into the next batch if needed), then the request is sent. This
   step holds a lock, so concurrent requests cannot all pass the check.

"Not fetched yet" and "last refresh failed" both count as zero remaining, so
restricted models return 429. The error message distinguishes "quota
insufficient" from "quota information unavailable"; the code is the same.

Refunds:

- The request could not be sent (connection failure, credential unavailable): refund.
- The upstream returned a non-2xx status: refund.
- Everything else is not refunded, including a read timeout (the request was
  already sent and may be billed), a stream that breaks mid-response, or a
  client cancellation.
- A refund goes back to the batch it was deducted from; if that batch has
  already expired, it is not refunded.

This is deliberately conservative: cases where the upstream did not charge are
still not refunded, and an upstream that does charge on non-2xx is discovered
by calibration.

### Refresh scheduling

- **At startup**: one synchronous fetch in `initialize_app`, bounded by
  `command_timeout_seconds`. A failure does not prevent startup; restricted
  models are simply rejected until a later success.
- **Afterwards**: a background thread refreshes every
  `refresh_interval_seconds`. On failure it retries every 60 seconds until
  success.
- **Config hot reload**: changing `command` or `command_timeout_seconds`
  clears that profile's ledger and fetches immediately; deleting a profile
  drops its ledger. Changing `min_remaining` or `quota_cost` does not trigger a
  re-fetch.
- Only one refresh runs per profile at a time, and the command never holds the
  ledger lock, so requests are not slowed by it.

When a refresh completes, the new ledger = fetched data (minus expired
batches). Requests still in flight are not deducted again: the upstream may or
may not have counted them yet. The ledger is therefore approximate between
refreshes, off by roughly (requests in flight at refresh time × `quota_cost`);
`min_remaining` is the buffer for that.

### Calibration and alerts

After each successful fetch, the ledger as it stood when the fetch started is
compared with the fetched data per batch (by `expires_at`):

- Our ledger higher than fetched means the upstream charged more than we
  recorded: emit an alert.
- Our ledger lower is expected (`quota_cost` set high): no alert.
- A new batch in the fetched data that our ledger lacks: no alert.
- An unexpired batch in our ledger that the fetched data lacks counts as 0
  fetched (used up upstream). Expired batches are not compared.
- A difference below 0.01 points: no alert.
- No comparison if the previous fetch failed (the ledger was cleared), nor on
  the first fetch.

An alert records time, profile, batch (expiry), our value, fetched value and
the difference. Alerts are **in-memory only, at most 50 per profile, and are
lost on restart**. The ledger then adopts the fetched data.

### Dashboard

`GET /api/quota` returns, for every profile with a `quota` block: current
remaining points, `min_remaining`, each batch (amount, expiry, time left), last
fetch / last success / last error, and the alert list. The dashboard shows a
block for these values, hidden when no profile configures a quota.

The endpoint contains numbers only — no credentials or command content. Like
`/api/stats` and the other dashboard endpoints, it is not in `PROTECTED_PATHS`
and needs no token when authentication is enabled.

### Limits

- No persistence: ledger and alerts are in memory and rebuilt by a refresh
  after restart.
- Per-request charging only, not per token: each request deducts a fixed
  `quota_cost`.
- Single process by default: multiple processes keep separate ledgers and only
  discover divergence through calibration.
- No retries or queuing: insufficient quota returns 429 immediately.
- `quota_cost` is not learned automatically.
- Requests in flight during a refresh are not re-deducted. If the upstream
  charges only when a request completes, the new ledger can be higher than
  reality until the next refresh, and the next calibration may report that
  difference as an alert. Keep `min_remaining` as a buffer.
- A refund that straddles a refresh (deducted before it, refunded after it)
  can leave the ledger off by one `quota_cost` until the next refresh.
- With `max_connection_retries > 0`, a read timeout is retried, so one
  deduction can be billed upstream more than once. Prefer leaving it at 0 for
  APIs serving quota-limited models.

## Authentication

### No upstream authentication

```yaml
auth:
  type: none
```

### Bearer token from an environment variable

```yaml
auth:
  type: bearer_env
  env: PRIVATE_LLM_TOKEN
```

### Bearer token from a command

```yaml
auth:
  type: bearer_command
  command:
    - credential-helper
    - get-token
  cache_ttl_seconds: 3000
  command_timeout_seconds: 30
```

The command is executed directly without a shell. Its trimmed stdout is used as the token. A non-zero exit code or empty stdout fails only the affected proxy request. Tokens are never placed in the request cache or returned by the model-list endpoint.

### Custom header from a command

Use `header_command` for upstreams that require a credential in a custom header without a `Bearer` prefix:

```yaml
auth:
  type: header_command
  header: api-key
  command:
    - cat
    - /path/to/private-key.txt
```

`header` is required and must be a valid HTTP header name (no whitespace, colons, or control characters). It does not default to `Authorization`; specify that name explicitly if the upstream expects a raw Authorization value. A client-supplied header with this name is omitted from cached request headers; it is not used as the upstream credential.

Both command auth types use the same command execution, token cache, and timeout settings. A 401 response invalidates a command-backed token and retries once. A second 401 is returned without another retry.

## Headers

Outbound headers are merged in this order:

1. `Content-Type: application/json`
2. Profile `headers`
3. API `headers`
4. Model `headers`
5. Model API `headers`
6. Dynamic header bindings
7. Affinity header
8. Upstream authentication

Later values override earlier values, case-insensitively for steps 6–8. Authentication is applied last: a binding or affinity header with the same name cannot replace the credential. Use distinct names if the upstream needs both authentication and routing values.

Empty string values are preserved. Static headers replaced by upstream authentication or dynamic bindings do not require their `${ENV_VAR}` placeholders to be set.

Header values support `${ENV_VAR}` interpolation:

```yaml
headers:
  X-Tenant: "${PRIVATE_LLM_TENANT}"
```

Incoming client headers are not forwarded, except for the names explicitly listed in `header_bindings` below. In particular, a ghc-api user token is never reused as an upstream credential.

## Dynamic header bindings

Forwarding a client-supplied header stays opt-in: an API config may declare `header_bindings`, and only those exact client header names are ever read from the incoming request.

```yaml
apis:
  messages:
    upstream_url: https://private-llm.example.com/v1/messages
    header_bindings:
      - client_name: X-Client-Session
        upstream_name: X-Upstream-Session
        value_type: uuid_v4
```

Fields, all required:

- `client_name`: the header name read from the client request and echoed on the ghc-api response.
- `upstream_name`: the header name sent upstream with the same value.
- `value_type`: currently only `uuid_v4`.

Behavior:

- If the client sends `client_name`, the value must parse as a UUID version 4. It is normalized to canonical lower-case form, so a re-sent value keeps the same upstream session. An invalid value fails the request with HTTP 400 before any upstream call.
- If the client omits the header, ghc-api generates a fresh UUID v4 per request.
- The resolved value is returned to the client in `client_name` on success and on proxy-generated errors, so a client can capture it and reuse it.
- The value replaces any static header of the same `upstream_name`, including a differently-cased spelling, and an unused `${ENV_VAR}` placeholder on that static header is not resolved.
- `client_name` is omitted from the request cache, the request browser and exports; the upstream value is never published by `/proxy/models`.
- `/proxy/models` publishes only the client-facing names for the built-in Chat page, as `request_headers: {"/messages": [{"name": ..., "value_type": ...}]}`.

Validation rejects the configuration when:

- a name is not a valid HTTP token, or is a structural header such as `host` or `content-type`;
- a name is a credential header (for example `authorization`, `x-api-key`, `api-key`, `x-auth-token`, or any `*-api-key`, `*-auth-token`, `*-access-token`, `*-secret` name), using the same predicate that redacts credentials from the cache;
- `client_name` and `upstream_name` are equal, or two bindings of one API overlap;
- a name reuses the profile's affinity `request_header` or `response_header`, which would otherwise overwrite the affinity token.

## Model field handling

Each API config selects one model-field mode:

- `preserve`: send the public model id received from the client.
- `omit`: remove `model` before forwarding.
- `upstream`: replace `model` with the model API's `upstream_model` value.

Example:

```yaml
apis:
  chat_completions:
    request_model: upstream

models:
  public-model:
    apis:
      chat_completions:
        upstream_model: private-deployment
```

`response_model: public` rewrites model identifiers in successful JSON responses and SSE events back to the public model id. It does not modify tool calls, reasoning items, encrypted content, item ids, or usage.

## Affinity routing

Some gateways return a response header that must be included on later requests routed to the same upstream partition.

```yaml
affinity:
  enabled: true
  response_header: X-Route-Token
  request_header: X-Route-Token
  scope: model
  persist: true
```

Supported scopes:

- `proxy`: one token per profile/API/upstream URL.
- `model`: one token per profile/API/public model/upstream URL.

Responses, Chat Completions, and Messages always use separate affinity keys. First-request discovery is serialized per key so concurrent cold requests do not establish conflicting routes.

Affinity values are persisted atomically and are not exposed through the API or dashboard.

## Built-in Chat page and accounting

The built-in `/chat` page loads both Copilot models and configured-proxy models. Configured models are grouped by profile, and Chat, Raw, and Decision modes send requests directly to the selected profile's `/proxy/<profile>/v1/...` route. Model ids remain the public ids declared in this file.

Configured-proxy requests use the same request cache, request browser, in-memory statistics, per-user statistics, persisted request JSONL, request-file statistics, and token-usage reporter as the existing endpoints. Token fields are extracted using the matching API shape:

- Responses: `input_tokens`, `output_tokens`, and `input_tokens_details.cached_tokens`.
- Chat Completions: `prompt_tokens`, `completion_tokens`, and `prompt_tokens_details.cached_tokens`.
- Anthropic Messages: `input_tokens`, `output_tokens`, `cache_creation_input_tokens`, and `cache_read_input_tokens`.
- System One: `input_tokens` and `output_tokens`.

The Chat page requests streaming usage from Chat Completions backends with `stream_options.include_usage`, since standards-compliant OpenAI-compatible servers otherwise commonly omit usage from streaming chunks. Messages-only models are also available in the built-in Chat page. Error responses are recorded with zero usage, matching the existing endpoints.

## Native System One decisions

The `systemone` API forwards decision requests without translation. A decision model does not generate text; it scores a closed set of options and returns a calibrated probability per option.

```yaml
proxies:
  example-decision:
    auth:
      type: none
    apis:
      systemone:
        upstream_url: https://example.services.ai.azure.com/providers/microsoft/v1/systemone
        timeout_seconds: 60
        request_model: upstream
        response_model: public
        headers:
          api-key: "${EXAMPLE_DECISION_API_KEY}"
    models:
      microsoft-decision-1:
        display_name: Microsoft Decision 1
        context_window: 32000
        apis:
          systemone:
            upstream_model: example-decision-deployment
```

Every field except `model` is forwarded unchanged in both directions. `model` follows the configured `request_model` and `response_model` rules, so with the profile above a client sends and receives the public id `microsoft-decision-1` while the upstream sees the deployment name `example-decision-deployment`. Use `request_model: preserve` and `response_model: preserve` for byte-equivalent model values.

```json
{
  "model": "microsoft-decision-1",
  "state": "The payment callback API returns 500 on every call.",
  "questions": {
    "team": {
      "type": "choice",
      "instructions": "Which team should handle this ticket?",
      "criteria": {
        "billing": "Charges, invoices, and refunds",
        "engineering": "Bugs, errors, and outages"
      }
    }
  }
}
```

Behavioural notes:

- **Non-streaming only.** A request with `"stream": true` is rejected with HTTP 400 `unsupported_stream` and never reaches the upstream.
- **`request_model: omit` is rejected at config load.** The upstream resolves the deployment from the request body, so `model` must be `preserve` or `upstream`. With `upstream`, the public model id maps to the upstream deployment name.
- `response_model: public` matters here because the upstream reports the underlying model name in `model`, not the deployment name it was called with.
- Usage accounting reads the flat `usage.input_tokens` and `usage.output_tokens` fields. Decision models have no cache tiers, so cached-token counters stay at zero.
- Question and answer bodies are not inspected, validated, or rewritten. Upstream validation errors (HTTP 422) are returned unchanged.
- Decision models appear in `GET /proxy/models` and `GET /proxy/<profile>/v1/models` with `supported_endpoints: ["/systemone"]`. The built-in `/chat` page lists them with a `[decision]` tag and sends them to `/proxy/<profile>/v1/systemone` from its Decision mode (or Raw mode); Chat mode does not use them because they return probabilities rather than messages.

Calling it through ghc-api:

```bash
curl http://127.0.0.1:8313/proxy/example-decision/v1/systemone \
  -H "Content-Type: application/json" \
  -d '{"model":"microsoft-decision-1","state":"...","questions":{...}}'
```

## Native Anthropic Messages

The Messages API is passed through without OpenAI translation. Both JSON and Anthropic SSE responses are supported. When `response_model: public` is configured, the top-level model in a JSON response and `message_start.message.model` in a stream are rewritten to the public model id; use `preserve` for byte-equivalent model values.

Configure required Anthropic headers such as `anthropic-version`, `anthropic-beta`, and `x-api-key` in the profile/API/model header sections. There is currently no configured-proxy `/v1/messages/count_tokens` route.

## Client configuration

### Pi using Responses

Add a provider to `~/.pi/agent/models.json`:

```json
{
  "providers": {
    "configured-proxy-responses": {
      "baseUrl": "http://127.0.0.1:8313/proxy/example-llm/v1",
      "api": "openai-responses",
      "apiKey": "not-needed",
      "models": [
        {
          "id": "example-coding-model",
          "reasoning": true
        }
      ]
    }
  }
}
```

### Pi using Chat Completions

```json
{
  "providers": {
    "configured-proxy-chat": {
      "baseUrl": "http://127.0.0.1:8313/proxy/example-llm/v1",
      "api": "openai-completions",
      "apiKey": "not-needed",
      "models": [
        {
          "id": "example-coding-model",
          "reasoning": true
        }
      ]
    }
  }

```

### Anthropic SDK using Messages

```python
from anthropic import Anthropic

client = Anthropic(
    base_url="http://127.0.0.1:8313/proxy/example-llm",
    api_key="not-needed",
)
message = client.messages.create(
    model="example-coding-model",
    max_tokens=1024,
    messages=[{"role": "user", "content": "Hello"}],
)
```

When ghc-api authentication is enabled, the SDK's `api_key` must be the normal ghc-api user token. Upstream credentials remain private in `upstream-proxies.yaml`.

### Codex using Responses

```toml
model_provider = "configured-proxy"
model = "example-coding-model"

[model_providers.configured-proxy]
name = "Configured Proxy"
base_url = "http://127.0.0.1:8313/proxy/example-llm/v1"

```

When ghc-api `enable_auth` is enabled, configure the normal ghc-api user token in the client. The `/proxy/...` blueprint enforces the same user registry independently of the legacy route allowlist.

## Failure isolation

- Missing private config: configured proxy profiles are unavailable; existing endpoints are unaffected.
- Invalid config reload: the last valid proxy snapshot remains active.
- Credential command failure: only that request returns 503.
- Upstream connection failure: only that request returns 503.
- Empty successful upstream body: returned as 502.
- Invalid streaming content type: returned as 502.
- Affinity persistence failure: logged without failing the current upstream response.
