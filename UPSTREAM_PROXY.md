# Configured Upstream Proxy

The configured upstream proxy is an isolated, optional subsystem for forwarding OpenAI-compatible Responses and Chat Completions requests to private or self-hosted gateways.

It does not modify or share model routing with ghc-api's existing Copilot endpoints.

## Routes

For a profile named `example-llm`:

```text
POST /proxy/example-llm/v1/responses
POST /proxy/example-llm/v1/chat/completions
GET  /proxy/example-llm/v1/models
GET  /proxy/models
```

`GET /proxy/models` is a first-party discovery catalog used by the built-in `/chat` page. It adds the profile name and profile base URL to each public model entry without exposing upstream URLs, headers, credentials, or affinity values.

The existing `/v1/responses`, `/v1/chat/completions`, and `/v1/models` routes remain Copilot-only.

The legacy text Completions API (`/v1/completions`) is not part of this feature. `chat_completions` refers to `/v1/chat/completions`.

## Private configuration

The default private configuration path is:

- Windows: `%APPDATA%\ghc-api\upstream-proxies.yaml`
- Linux/macOS: `~/.ghc-api/upstream-proxies.yaml`

Override it with:

```text
GHC_API_PROXY_CONFIG=/path/to/private-proxies.yaml
```

Affinity state is stored separately in `proxy-affinity.json` under the ghc-api config directory. Override that path with `GHC_API_PROXY_AFFINITY_FILE`.

The proxy configuration is deliberately separate from `config.yaml`:

- It is not generated by `ghc-api --config`.
- It is not returned by `/api/runtime-config`.
- It is not merged into the existing Copilot model list.
- A missing or invalid file does not prevent the existing server from starting.
- On an invalid reload, the last valid in-memory configuration remains active.

Start from [`upstream-proxies.example.yaml`](upstream-proxies.example.yaml), but keep real endpoints, credential commands, headers, and model routes outside the repository.

## Profile configuration

```yaml
proxies:
  example-llm:
    enabled: true

    auth:
      type: bearer_env
      env: EXAMPLE_LLM_TOKEN

    headers:
      X-Quota-Id: ""

    affinity:
      enabled: true
      response_header: X-Route-Token
      request_header: X-Route-Token
      scope: model
      persist: true

    apis:
      responses:
        upstream_url: https://gateway.example.test/responses
        request_model: omit
        response_model: public

      chat_completions:
        upstream_url: https://gateway.example.test/chat/completions
        request_model: upstream
        response_model: public
        accept_mislabeled_sse: false

    models:
      example-coding-model:
        display_name: Example Coding Model
        reasoning: true
        input: [text]
        context_window: 128000
        max_output_tokens: 16384
        headers:
          X-Upstream-Model: example-route
        apis:
          responses:
            upstream_model: null
          chat_completions:
            upstream_model: example-chat-deployment
```

Profile names may contain only letters, digits, `.`, `_`, and `-`.

## Authentication

### No upstream authentication

```yaml
auth:
  type: none
```

### Bearer token from an environment variable

```yaml
auth:
  type: bearer_env
  env: PRIVATE_LLM_TOKEN
```

### Bearer token from a command

```yaml
auth:
  type: bearer_command
  command:
    - credential-helper
    - get-token
  cache_ttl_seconds: 3000
  command_timeout_seconds: 30
```

The command is executed directly without a shell. Its trimmed stdout is used as the token. A non-zero exit code or empty stdout fails only the affected proxy request. Tokens are never placed in the request cache or returned by the model-list endpoint.

A 401 response invalidates a command-backed token and retries once.

## Headers

Outbound headers are merged in this order:

1. `Content-Type: application/json`
2. Profile `headers`
3. API `headers`
4. Model `headers`
5. Model API `headers`
6. Upstream authentication
7. Affinity header

Later values override earlier values. Empty string values are preserved.

Header values support `${ENV_VAR}` interpolation:

```yaml
headers:
  X-Tenant: "${PRIVATE_LLM_TENANT}"
```

Incoming client headers are not forwarded. In particular, a ghc-api user token is never reused as an upstream credential.

## Model field handling

Each API config selects one model-field mode:

- `preserve`: send the public model id received from the client.
- `omit`: remove `model` before forwarding.
- `upstream`: replace `model` with the model API's `upstream_model` value.

Example:

```yaml
apis:
  chat_completions:
    request_model: upstream

models:
  public-model:
    apis:
      chat_completions:
        upstream_model: private-deployment
```

`response_model: public` rewrites model identifiers in successful JSON responses and SSE events back to the public model id. It does not modify tool calls, reasoning items, encrypted content, item ids, or usage.

Streaming responses must normally use `Content-Type: text/event-stream`. For a known-compatible upstream that emits valid OpenAI SSE fields under an incorrect content type, opt in per API:

```yaml
apis:
  chat_completions:
    accept_mislabeled_sse: true
```

The strict content-type check remains the default. Chat Completions streaming also normalizes a bare `[DONE]` line from non-conforming upstreams to the standard `data: [DONE]` sentinel.

## Affinity routing

Some gateways return a response header that must be included on later requests routed to the same upstream partition.

```yaml
affinity:
  enabled: true
  response_header: X-Route-Token
  request_header: X-Route-Token
  scope: model
  persist: true
```

Supported scopes:

- `proxy`: one token per profile/API/upstream URL.
- `model`: one token per profile/API/public model/upstream URL.

Responses and Chat Completions always use separate affinity keys. First-request discovery is serialized per key so concurrent cold requests do not establish conflicting routes.

Affinity values are persisted atomically and are not exposed through the API or dashboard.

## Built-in Chat page and accounting

The built-in `/chat` page loads both Copilot models and configured-proxy models. Configured models are grouped by profile, and both Chat mode and Raw mode send requests directly to the selected profile's `/proxy/<profile>/v1/...` route. Model ids remain the public ids declared in this file.

Configured-proxy requests use the same request cache, request browser, in-memory statistics, per-user statistics, persisted request JSONL, request-file statistics, and token-usage reporter as the existing endpoints. Token fields are extracted using the matching API shape:

- Responses: `input_tokens`, `output_tokens`, and `input_tokens_details.cached_tokens`.
- Chat Completions: `prompt_tokens`, `completion_tokens`, and `prompt_tokens_details.cached_tokens`.

The Chat page requests streaming usage from Chat Completions backends with `stream_options.include_usage`, since standards-compliant OpenAI-compatible servers otherwise commonly omit usage from streaming chunks. Error responses are recorded with zero usage, matching the existing endpoints.

## Client configuration

### Pi using Responses

Add a provider to `~/.pi/agent/models.json`:

```json
{
  "providers": {
    "configured-proxy-responses": {
      "baseUrl": "http://127.0.0.1:8313/proxy/example-llm/v1",
      "api": "openai-responses",
      "apiKey": "not-needed",
      "models": [
        {
          "id": "example-coding-model",
          "reasoning": true
        }
      ]
    }
  }
}
```

### Pi using Chat Completions

```json
{
  "providers": {
    "configured-proxy-chat": {
      "baseUrl": "http://127.0.0.1:8313/proxy/example-llm/v1",
      "api": "openai-completions",
      "apiKey": "not-needed",
      "models": [
        {
          "id": "example-coding-model",
          "reasoning": true
        }
      ]
    }
  }
}
```

### Codex using Responses

```toml
model_provider = "configured-proxy"
model = "example-coding-model"

[model_providers.configured-proxy]
name = "Configured Proxy"
base_url = "http://127.0.0.1:8313/proxy/example-llm/v1"
wire_api = "responses"
```

When ghc-api `enable_auth` is enabled, configure the normal ghc-api user token in the client. The `/proxy/...` blueprint enforces the same user registry independently of the legacy route allowlist.

## Failure isolation

- Missing private config: configured proxy profiles are unavailable; existing endpoints are unaffected.
- Invalid config reload: the last valid proxy snapshot remains active.
- Credential command failure: only that request returns 503.
- Upstream connection failure: only that request returns 503.
- Empty successful upstream body: returned as 502.
- Invalid streaming content type: returned as 502 unless that API explicitly sets `accept_mislabeled_sse: true`.
- Affinity persistence failure: logged without failing the current upstream response.
